# Security boundaries and recovery

This repository is a tested prototype, not a third-party audit. The local tests establish specific behaviours; they do not establish that arbitrary websites, tokens or contracts are safe.

## Enforced boundaries

- The owner, relayer, native budget, expiry, and optional target/function pairs are fixed at vault deployment. The contract supports no permission update or delegatecall. An empty permission list allows any call except known approval/transfer selectors.
- `spent` is cumulative native value, not an instantaneous balance check. Extra deposits never increase the allowance.
- Known approval/transfer selectors are blocked. The task wallet may sign login messages as itself; permit-style typed data is rejected. This is not a universal detector for every custom approval-like function.
- All recovery goes to the immutable owner. Closing and transferring assets are separate operations. The owner may call recovery directly if the API is unavailable.
- API keys can inspect and operate existing authorized sessions, but cannot create an allowance, manage keys, request owner swaps, or register new recovery tokens. Revocation takes effect on the next request; it does not cancel submitted work.
- Privy tokens are verified server-side and wallets are obtained from the verified user. Local sign-in is loopback-only and disabled in configured mode. Cookie writes require the correct origin.
- Each browser has a fresh context and separate Chromium process. Credentials are excluded from its environment. The provider exists only in the main frame at the approved origin.
- Resource hosts must be public. Private networks, service workers, WebSockets, popups and downloads are blocked. Chromium sandboxing is requested. Production still needs host-level network/process isolation; URL checks are not a substitute for it.
- Known service credentials and RPC URLs are redacted from user-facing/persisted errors. API keys are displayed once and only their SHA-256 hashes are retained.

## Supported assets and trust

Execution supports native-value contract calls. Automatic discovery uses standard Transfer events in confirmed execution receipts. Recovery supports native currency, ERC-20 balances, and ERC-721 IDs. ERC-1155, rebasing semantics, staking positions, nonstandard assets, signature login and ERC-20-spending dapps are unsupported. A malicious token can refuse transfer; that asset remains recoverable only according to its contract behaviour. Event logs are evidence, not a guarantee that a token is genuine.

The permitted dapp can use any funds passed to it within the native budget. Selectors alone cannot judge pricing, calldata recipients, business outcomes or a malicious implementation. Browser content and model output cannot expand the contract's permission, but can misuse an allowed function. The relayer pays gas separately: the native task budget is not a total gas-inclusive invoice. The app caps submitted execution count and per-execution gas, but a public service additionally needs economic admission control, relayer policies and monitoring.

The chain/RPC and Privy app credentials are trusted components. The relayer retains bounded execution until expiry or closure. It cannot rewrite a vault's recovery address. A compromised owner wallet is outside this boundary. Playwright's browser profile is ephemeral; chain history is public and permanent. Closing does not erase identity links or guarantee anonymity.

## Direct owner recovery

Use the verified deployment ABI or the ABI generated by Foundry. From the immutable owner wallet, call `close()`, then `recoverNative()`, `recoverERC20(token)` or `recoverERC721(token,id)`. These require ordinary gas. Recovery remains available after expiry and after earlier recovery. The owner can find the vault and asset IDs in a saved JSON receipt. No deleted ephemeral private key is required.

The UI's **End & return everything**, **Retry recovery**, **Check for late funds** and **Recover another asset** use the same fixed-destination contract methods. Do not send unsupported assets to a task vault.

## Dependencies

Compatible updates removed the two high-severity dependency advisories found during this build. The latest recorded audit has no high/critical findings and 23 moderate transitive findings through Privy's optional wallet connector tree, rooted in older `uuid` and `decode-uri-component` dependencies. We did not force incompatible major overrides or downgrade Privy merely to silence the report. Recheck the lockfile before publishing; these counts can change. This is not a zero-vulnerability claim.
