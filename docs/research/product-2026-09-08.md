# Melt: product research, 8 September 2026

This pass is for making Melt a usable product, not for claiming a prize. X was not signed in for this run, so live timeline search was unavailable. Public X posts already captured on 7 September, first-party docs, GitHub READMEs, ETHOnline prize pages, and Stripe’s webhook/invoice docs were used instead.

## Decision

Do not become another “agent wallet.” MetaMask Agent Wallet (Guard/Beast, 8 June 2026), Coinbase Agentic Wallets, and Privy’s policy engine already sell that category. ETHOnline is full of Uniswap-trading agent cities and x402 marketplaces.

Melt’s job is a **closed task**: an isolated browser, an onchain spending vault the agent cannot raise, a public receipt anyone can open, HMAC-signed webhooks for the owner’s server, and recovery that still works when Melt is offline. That is the Stripe analog (PaymentIntent + hosted invoice + `Stripe-Signature` + Events), applied to one agent job.

## What people actually need

Verified from vendor docs and competing hackathon READMEs, not from a new X scrape:

- **Limits the model cannot talk its way around.** Privy’s agent-wallet docs and MetaMask’s 6 July 2026 lifecycle article both treat planner-enforced caps as the wrong boundary. Froggy’s README states the same rule in product language: there is no `raise_limit` tool.
- **Proof of what happened, shareable without the dashboard.** Stripe’s hosted invoice page exists so a customer can see status and amounts from a secret URL. SBO3L (ETHGlobal Open Agents 2026) is building signed policy receipts because “the agent did something” is not an audit trail. Froggy files receipts under chat turns; they are not a public URL a third party can open.
- **A way to stop polling.** Stripe’s webhook guide is still the developer expectation: HTTPS endpoint, raw-body HMAC, `t=,v1=` header, secret shown once, dashboard event log, Send test.
- **Recovery after the worker dies.** Froggy’s 8 September README still lists durable funding confirmation and partial-allocation recovery as open backend work. Compromised-wallet recovery articles (Bankless / EIP-7702 rescue tools) are a different problem, but they show the user fear: funds stuck in a hot path they no longer control.

## Stripe mapping (what shipped in this pass)

| Stripe                                                                     | Melt                                                   |
| -------------------------------------------------------------------------- | ------------------------------------------------------ |
| PaymentIntent + mandate copy                                               | Session + English `mandateText`                        |
| `hosted_invoice_url`                                                       | `/r/{token}` and `GET /api/public/receipts/{token}`    |
| Dashboard Events                                                           | Developers → Events (`GET /api/events`)                |
| Webhooks + `Stripe-Signature` `t=,v1=` HMAC over raw body, `whsec_` secret | `Melt-Signature`, same construction, secret shown once |
| `constructEvent`                                                           | `constructEvent` in the one-file client                |
| Customer receipt without login                                             | Public receipt omits `userId`                          |

Sources: [Stripe hosted invoice page](https://docs.stripe.com/invoicing/hosted-invoice-page), [Stripe webhook signatures](https://docs.stripe.com/webhooks/signatures).
