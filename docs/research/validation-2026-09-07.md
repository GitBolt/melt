# Melt: research and build decision

Research date: September 7, 2026. This is a targeted review of current products, public submissions, official rules and selected X/Discord material, not an exhaustive inventory or a guarantee of originality or prize eligibility.

## Decision

Build a **wallet for one browser task**. The owner grants a specific site a bounded contract permission; an agent completes a small onchain action; Melt closes spending access, returns the result and unused funds, and keeps owner recovery available. The first job is buying/minting one collectible from a website. Keep the product this specific.

The implementation's strongest demonstration is the whole lifecycle: create → funded isolated browser → denied oversized spend → valid mint → close → return → later recovery. Bounded agent wallets and browser handoff already exist. We should compete on how clearly and reliably this lifecycle works, not describe those primitives as inventions.

## Twitter / X checks actually performed

Read live X search results for `"agent wallet"`, `from:privy_io (agent OR passkey)`, and `from:MetaMask "agent"`. Broad results contained substantial repeated promotion; no engagement count or launch thread was treated as proof of user demand.

- [Privy, July 10](https://x.com/privy_io/status/2075637161295073785): AgentCore/payment architecture separates limits from signing and keeps wallet keys outside the agent. This supports using external enforcement, but does not validate demand for Melt.
- [Privy, August 14](https://x.com/privy_io/status/2088305416660988410): current messaging includes delegated/sponsored wallets, SIWE and multiple integration surfaces. Modern onboarding should accommodate wallet users and email users.
- [MetaMask, August 19](https://x.com/MetaMask/status/2090227262423740439) and [August 11](https://x.com/MetaMask/status/2087248279650324814): the agent-wallet launch and CLI/security-stack positioning further confirm an established category. It is not credible to sell basic agent-wallet access as new.

Technical choices were checked against primary documentation rather than inferred from social posts: [Privy embedded-wallet creation](https://docs.privy.io/basics/react/advanced/automatic-wallet-creation), [Privy token verification](https://docs.privy.io/authentication/user-authentication/access-tokens), [Privy policies](https://docs.privy.io/controls/policies/overview), and [Uniswap's integration guide](https://developers.uniswap.org/docs/trading/swapping-api/start-building/integration-guide). Email plus embedded wallets, optional passkeys, owner-reviewed transactions and backend-verified identity are implemented. Wallet connection remains available.

The [earlier Discord notes](../competition-2026-09-07.md) are retained as a dated snapshot. Those searches surfaced Froggy and adjacent projects; they were not an audit of every channel/member's work. During the later research pass Safari was being used by the user, so I stopped operating it and used a separate research browser for X. No Discord message or check-in was posted.

**Recommendation:** earn the Privy and Uniswap claims with recorded execution first. Use Bazantic as the third option only if its gateway/recipe can demonstrate a real completed job with the existing API. The project has no implementation-based claim to the remaining tracks today. Do not stretch the app into a marketplace, a social network, or an unrelated stablecoin platform merely to name more sponsors.

## What would actually improve winning chances

1. Record one real model-driven transaction lifecycle on a public testnet using Privy. Prove the denied call and the allowed outcome with receipts.
2. Test one unaffiliated compatible dapp with a narrow native-value action. Both local fixture themes share our code; they are not proof of broad compatibility.
3. Show owner recovery after a stopped/restarted agent and after a late deposit. This is a clearer differentiator than a list of agent acronyms.
4. Ask mentors whether this specific lifecycle is sufficiently distinct from Froggy and whether the owner-controlled conversion is substantial enough for Uniswap. Use the concrete check-in draft, not “idea TBD.”
5. Validate usefulness with a few actual agent builders: ask for a task they already avoid because they would need to give an agent their main wallet. Competitor overlap validates a category; it does not replace these conversations.

Build scope is intentionally precise. The current UI and lifecycle can be demonstrated locally without external dependencies. Model quality, live provider compatibility, public deployment and user demand still require evidence.
